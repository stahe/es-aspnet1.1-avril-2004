    7. ASP Componentes del servidor - 1

    7.1. Introducción

    En este capítulo, describimos la tecnología recomendada en ASP.NET para construir la interfaz de usuario. Sabemos que hay dos fases distintas en el procesamiento de una página .aspx por parte del servidor web:

    1. En primer lugar, se ejecuta el controlador de la página. Consiste en código ubicado dentro de la propia página .aspx (solución WebMatrix) o en un archivo independiente (solución Visual Studio.NET).
    2. A continuación, se ejecuta el código de presentación de la página .aspx y se convierte en código HTML que se envía al cliente.

    ASP.NET ofrece tres bibliotecas de etiquetas para escribir el código de presentación de la página:

    1. Etiquetas clásicas HTML. Esto es lo que hemos estado utilizando hasta ahora.
    2. etiquetas HTML del lado del servidor
    3. Etiquetas de formularios web

    Independientemente de la biblioteca de etiquetas que se utilice, la función del controlador de página sigue siendo la misma. Debe calcular el valor de los parámetros dinámicos que aparecen en el código de presentación. Hasta ahora, estos parámetros dinámicos eran sencillos: eran objetos de tipo [String]. Así, si en el código de presentación tenemos una etiqueta <%=nombre%>:

    • el controlador de página declara una variable [name] de tipo [String] y calcula su valor
    • cuando el controlador de la página ha terminado su trabajo y se ejecuta el código de presentación para generar la respuesta HTML, la etiqueta <%=nombre%> se sustituye por el valor calculado por el código del controlador

    Sabemos que la separación controlador/vista es arbitraria y que el código del controlador y el de la vista pueden mezclarse en la misma página. Hemos explicado por qué se desaconseja este enfoque, y seguiremos adhiriéndonos a la separación controlador/vista.

    Las etiquetas [server HTML] y [WebForms] permiten incluir en el código de presentación objetos más complejos que el simple objeto [String]. Esto a veces puede ser muy útil. Tomemos el ejemplo de un formulario con una lista. Esta lista debe ser presentada al cliente con código HTML que se parece a esto:

    <select name="uneListe" size="3">
    <option value="opt1">option1</option>
    <option value="opt2">option2</option>
    <option value="opt3" selected>option3</option>
</select>

    El contenido de la lista y la opción a seleccionar son elementos dinámicos y, por tanto, deben ser generados por el controlador de página. Ya nos hemos encontrado con este problema y lo hemos resuelto incluyendo la etiqueta 

    <%=uneListeHTML%>

    Esta etiqueta será reemplazada por el valor [String] de la variable [uneListeHTML]. Este valor, calculado por el controlador, debe ser el código HTML de la lista, i.e., "<select name=..>...</select>". Esto no es particularmente difícil de hacer y parece una solución elegante que evita poner código de generación directamente en la capa de presentación de la página. En este caso, habría un bucle con pruebas que insertar en él, que quedaría así muy "desordenado" Sin embargo, este método tiene un inconveniente. La separación del control y la presentación en una página también sirve para delimitar dos áreas de responsabilidad:

    • la del desarrollador .NET, que se encarga del controlador de la página,
    • la del diseñador gráfico, que se encarga de la parte de presentación de la página

    Aquí vemos que la generación del código HTML para la lista se ha trasladado al controlador. El diseñador gráfico puede querer modificar este código HTML para cambiar el aspecto "visual" de la lista. Se vería obligado a trabajar en la sección [controlador] y, por tanto, saldría de su área de especialización, con el riesgo asociado de introducir errores en el código sin darse cuenta.

    Las bibliotecas de etiquetas de servidor resuelven este problema. Proporcionan un objeto que representa una lista HTML. Por ejemplo, la biblioteca [WebForms] ofrece la siguiente etiqueta:

    <asp:ListBox id="aList" runat="server"></asp:ListBox>

    Esta etiqueta representa un objeto [ListBox] que puede ser manipulado por el controlador de página. Este objeto tiene propiedades para representar las distintas opciones de la lista HTML y para designar la opción seleccionada. Por lo tanto, el controlador de página asignará los valores apropiados a estas propiedades. Cuando se ejecuta la capa de presentación, la etiqueta 

    <asp:ListBox id="aList" runat="server"></asp:ListBox>

    será sustituido por el código HTML que representa el objeto [uneListe], i.e., el código "<select ..>...</select>". Por ahora, no hay ninguna diferencia fundamental con el método anterior, aparte de un enfoque de codificación orientado a objetos, lo cual es interesante. Volvamos a nuestro diseñador gráfico, que necesita modificar el "aspecto" de la lista. Las etiquetas de servidor tienen atributos de estilo (BackColor, Bordercolor, BorderWidth, ...) que permiten establecer el aspecto visual del objeto HTML correspondiente. Así que podemos escribir:

    
                <asp:ListBox id="ListBox1" runat="server" BackColor="#ffff99"></asp:ListBox></P>

    La ventaja es que el diseñador gráfico trabaja directamente dentro del código de la presentación para realizar estos cambios. Esto supone una clara ventaja sobre el método anterior. Así pues, las bibliotecas de etiquetas del lado del servidor simplifican la construcción de la capa de presentación de las páginas web, a la que en capítulos anteriores nos hemos referido como interfaz de usuario. El propósito de este capítulo es presentarlas. Veremos que a veces ofrecen objetos complejos, como calendarios o tablas vinculadas a fuentes de datos. Son extensibles, lo que significa que el usuario puede crear su propia biblioteca de etiquetas. Así, puede crear una etiqueta que genere un banner en una página. Todas las páginas que utilicen esta etiqueta tendrán el mismo banner.

    El HTML generado para una etiqueta se adapta al tipo de navegador del cliente. Cuando el navegador envía una petición al servidor web, incluye una cabecera [User-Agent: xx] entre sus cabeceras HTTP, donde [xx] identifica al cliente. He aquí un ejemplo:

    User-Agent: Mozilla/5.0 (Windows; U; Windows NT 5.1; en-US; rv:1.7b) Gecko/20040316

    Con esta información, el servidor web puede determinar las capacidades del cliente, en particular el tipo de código HTML que puede manejar. A lo largo del tiempo, ha habido varias versiones del lenguaje HTML. Los navegadores modernos soportan las últimas versiones del lenguaje, mientras que los antiguos no. Basándose en la cabecera HTTP [User-Agent:] enviada por el cliente, el servidor devolverá una versión HTML que el cliente pueda entender. Este es un enfoque útil y práctico porque significa que el desarrollador no tiene que preocuparse por el tipo específico de navegador cliente utilizado por su aplicación.

    Por último, los IDEs avanzados, como Visual Studio.NET, WebMatrix, etc., permiten un diseño "estilo Windows" de la interfaz web. Aunque estas herramientas no son esenciales, proporcionan una ayuda significativa al desarrollador. El desarrollador diseña la interfaz web utilizando componentes gráficos que coloca en la interfaz. Tiene acceso directo a las propiedades de cada componente de la interfaz, que puede configurar a su gusto. Estas propiedades se traducen en el código de presentación HTML de la interfaz como atributos de la etiqueta <asp:> del componente. La ventaja para el desarrollador es que no tiene que memorizar ni la lista ni la sintaxis de los atributos de cada etiqueta. Esta es una ventaja significativa cuando uno no está completamente familiarizado con las librerías de etiquetas de servidor ofrecidas por ASP.NET. Una vez dominada esta sintaxis, algunos desarrolladores pueden preferir codificar las etiquetas directamente en el código de presentación de la página sin pasar por la fase de diseño gráfico. Entonces ya no es necesario un IDE; basta con un simple editor de texto. Dependiendo de su flujo de trabajo, la atención se centra entonces en los componentes (utilizando un IDE) o en las etiquetas (utilizando un editor de texto). Estos dos términos son equivalentes. Un componente es el objeto que será manipulado por el código de control de la página. El IDE nos da acceso a sus propiedades durante la fase de diseño. Los valores asignados a estas propiedades se traducen inmediatamente en los atributos de las etiquetas del componente en el código de presentación. Durante la fase de ejecución, el código de control de la página manipulará el componente y asignará valores a algunas de sus propiedades. El código de presentación generará el código HTML del componente utilizando, por un lado, los atributos establecidos durante el diseño para la etiqueta de servidor correspondiente y, por otro, los valores de las propiedades del componente calculados por el código de control.

    7.2. El contexto de ejecución de los ejemplos

    Ilustraremos el diseño de interfaces web basadas en componentes de servidor utilizando programas cuyo contexto de ejecución será mayoritariamente el siguiente:

    1. la aplicación web consistirá en una única página P que contendrá un formulario F,
    2. el cliente realizará su primera petición directamente a esta página P. Se tratará de solicitar el URL de la página P mediante un navegador. Se trata por tanto de una petición GET que se realizará a este URL P. El servidor entregará la página P y por tanto el formulario F que contiene,
    3. el usuario lo rellenará y lo enviará, i.e., realizará una acción que obligará al navegador a enviar el formulario F al servidor. La operación POST del navegador se dirigirá siempre a la página P. El servidor entregará de nuevo la página P con el formulario F, cuyo contenido puede haber sido modificado por la acción del usuario.
    4. A continuación, se reanudarán los pasos 2 y 3.

    Se trata de un proceso de ejecución muy específico, fuera del cual ya no funcionan ciertos conceptos que se discuten a continuación. Ya no estamos en un contexto de arquitectura MVC en el que una aplicación multipágina está controlada por una página específica que hemos denominado "controlador de la aplicación" En este tipo de arquitectura, los POSTs de formularios se dirigen al controlador y no a los propios formularios. Sin embargo, veremos que construir un formulario con componentes del lado del servidor implica que este formulario se publique a sí mismo.

    7.3. El componente etiqueta

    7.3.1. Utilización

    El <asp:etiqueta> permite insertar texto dinámico en el código de presentación de una página. Por lo tanto, no hace más que la etiqueta <%=variable%> utilizada hasta ahora. Estudiar esta primera etiqueta nos ayudará a entender cómo funcionan las etiquetas de servidor. Vamos a crear una página con una sección de control [form1.aspx.vb] y una sección de presentación [form1.aspx]. El objetivo es mostrar la hora:

    Esta cuestión ya se trató en el capítulo 2, y se recomienda al lector que lo consulte si desea saber cómo se trató. El código de presentación [form1.aspx] es el siguiente:

    
<%@ page src="form1.aspx.vb" inherits="form1" AutoEventWireup="false" %>
<HTML>
    <HEAD>
        <title>Web Forms</title>
    </HEAD>
    <body>
        <asp:Label Runat="server" ID="lblHeure" />
    </body>
</HTML>

    Introducimos el <asp:etiqueta> etiqueta. En las bibliotecas de etiquetas, el atributo [runat="server"] es obligatorio. El atributo ID identifica el componente. El controlador debe referenciarlo utilizando este identificador. El código del controlador [form1.aspx.vb] es el siguiente:

    
Imports System.Web.UI.WebControls
 
Public Class form1
    Inherits from System.Web.UI.Page
 
    Protected lblTime As Label
 
    Private Sub Page_Init(ByVal sender As Object, ByVal e As System.EventArgs) Handles MyBase.Init
        ' saves the current request to request.txt in the page's directory
        Dim requestFileName As String = Me.MapPath(Me.TemplateSourceDirectory) + "\request.txt"
        Me.Request.SaveAs(requestFileName, True)
    End Sub
 
    Private Sub Page_Load(ByVal sender As Object, ByVal e As System.EventArgs) Handles MyBase.Load
        ' sets the time in lblHeure
        lblTime.Text = "It is " + Date.Now.ToString("T")
    End Sub
 
End Class

    El controlador debe asignar un valor al objeto [lblHeure] de tipo [System.Web.UI.WebControls.Label]. Todos los objetos mostrados por las etiquetas <asp:> pertenecen al espacio de nombres [System.Web.UI.WebControls]. Por lo tanto, podemos importar sistemáticamente este espacio de nombres:

    
Imports System.Web.UI.WebControls

    El objeto [Label] tiene varias propiedades, incluida la propiedad [Text], que representa el texto que mostrará la etiqueta <asp:label> correspondiente. Aquí, establecemos esta propiedad a la hora actual. Esto lo hacemos en el procedimiento [Form_Load] del controlador, que siempre se ejecuta. En el procedimiento [Form_Init], que también se ejecuta siempre pero antes que el [Form_Load] almacenamos la petición del cliente en un archivo [request.txt] en la carpeta de la aplicación. Tendremos la oportunidad de examinar este archivo para comprender ciertos aspectos del funcionamiento de las páginas que utilizan etiquetas de servidor.

    El objeto [Label] tiene muchas propiedades, métodos y eventos. Se recomienda al lector que consulte la documentación sobre la clase [Label] para explorarlos. Este será el caso a lo largo del resto del libro. Para cada etiqueta, presentamos sólo las pocas propiedades que necesitamos.

    7.4. El componente literal

    7.4.1. Utilización

    El <asp:literal> permite insertar texto dinámico en el código de presentación de una página, de forma similar a la etiqueta <asp:label>. Su atributo principal es [Texto], que representa el texto que se insertará tal cual en el flujo HTML de la página. Esta etiqueta es suficiente si no tiene intención de dar formato al texto que desea insertar en el flujo HTML. En efecto, mientras que la clase [Label] permite dar formato utilizando atributos como [BorderColor, BorderWidth, Font, ...], la clase [Literal] no dispone de ninguno de estos atributos. El lector puede reproducir el ejemplo anterior en su totalidad sustituyendo el componente [Label] por un componente [Literal].

    7.5.5. Eventos en el ciclo de vida de una aplicación __TECHTERM_0

    La documentación ASP.NET enumera los eventos generados por el servidor durante el ciclo de vida de una aplicación:

    • Cuando la aplicación recibe su primera petición, se genera el evento [Start] en el objeto [HttpApplication] de la aplicación. Este evento puede ser manejado por el procedimiento [Application_Start] en el archivo [global.asax] de la aplicación.

    Next, we will have a series of events that will repeat for each request received:

    • si la solicitud no envió un testigo de sesión, se inicia una nueva sesión y se genera un evento [Start] en el objeto [Session] asociado a la solicitud. Este evento puede ser manejado por el procedimiento [Session_Start] en el archivo [global.asax] de la aplicación.
    • El servidor genera el evento [BeginRequest] en el objeto [HttpApplication]. Puede ser manejado por el procedimiento [Application_BeginRequest] en el archivo [global.asax] de la aplicación.
    • El servidor carga la página solicitada por la petición. Instanciará un objeto [Page] y generará dos eventos sobre este objeto: [Init] y [Load]. Estos dos eventos pueden ser manejados por los procedimientos [Page_Init] y [Page_Load] de la página.
    • En función de los valores publicados recibidos, el servidor generará otros eventos: [TextChanged] para un componente [TextBox] cuyo valor haya cambiado, [CheckedChanged] para un botón de radio cuyo valor haya cambiado, [SelectedIndexChanged] para una lista cuyo elemento seleccionado haya cambiado, ... Tendremos ocasión de mencionar los principales eventos para cada uno de los componentes del servidor que presentaremos. Cada evento E sobre un objeto llamado O puede ser manejado por un procedimiento llamado O_E.
    • El orden en el que se gestionan los eventos anteriores no está garantizado. Por lo tanto, los manejadores no deben hacer ninguna suposición sobre este orden. Sin embargo, podemos estar seguros de que el evento [Click] del botón que activó el POST se procesa en último lugar.
    • Una vez que la página esté lista, el servidor la enviará al cliente. Antes de hacerlo, genera el evento [PreRender], que puede ser manejado por el procedimiento [Page_PreRender] de la página.
    • Una vez que la respuesta HTML ha sido enviada al cliente, la página será descargada de la memoria. En este momento se generarán dos eventos: [Unload] y [Disposed]. La página puede utilizar estos eventos para liberar recursos.

    La aplicación también puede recibir eventos fuera de una solicitud de cliente:

    • El evento [End] en un objeto [Session] de una aplicación se produce cuando finaliza una sesión. Esto puede ocurrir por una petición explícita del código de una página o porque el tiempo de vida de la sesión ha expirado. El procedimiento [Session_End] en el archivo [global.asax] maneja este evento. Normalmente libera los recursos obtenidos en [Session_Start].
    • El evento [Fin] en el objeto [HttpApplication] de la aplicación se produce cuando la aplicación termina. Esto ocurre, por ejemplo, cuando se cierra el servidor web. El procedimiento [Application_End] en el archivo [global.asax] maneja este evento. Normalmente se utiliza para liberar recursos adquiridos en [Application_Start].

    Hay que tener en cuenta los siguientes puntos:

    • El modelo de eventos anterior se basa en intercambios estándar cliente-servidor HTTP. Esto es claramente evidente al examinar las cabeceras HTTP intercambiadas.
    • El procesamiento de los eventos anteriores siempre tiene lugar en el lado del servidor. Pulsar un botón puede, por supuesto, ser manejado por un script JavaScript del lado del servidor. Sin embargo, este no es un evento del servidor, y estamos tratando con una tecnología independiente de ASP.NET.

    ¿Cuándo se procesan los eventos, ya sea en el lado del servidor (eventos relacionados con componentes del servidor) o en el lado del navegador mediante scripts JavaScript?

    Tomemos el ejemplo de una lista desplegable. Cuando el usuario cambia el elemento seleccionado en ella, el evento (cambio del elemento seleccionado) puede procesarse o no, y si se procesa, puede procesarse en diferentes momentos.

    • If you want to process it immediately, there are two solutions:
      • Puede ser gestionado por el navegador mediante un script JavaScript. El servidor no interviene en este caso. Para que esto sea posible, la página debe poder reconstruirse utilizando valores presentes en ella.
      • Puede ser procesado por el servidor. Para ello, sólo hay una solución: el formulario debe enviarse al servidor para su procesamiento. Por lo tanto, tenemos una operación [submit]. Veremos que en este caso, utilizamos un componente de servidor llamado [DropDownList] y establecemos su atributo [AutoPostBack] a [true]. Esto significa que si el elemento seleccionado en la lista desplegable cambia, el formulario debe ser enviado inmediatamente al servidor. En este caso, el servidor genera código HTML para el objeto [DropDownList] que está asociado a una función JavaScript responsable de realizar un [submit] tan pronto como se produzca el evento "elemento seleccionado cambiado". Este [submit] enviará el formulario al servidor, y los campos ocultos se incluirán en el mensaje para indicar que el [post] es el resultado de un cambio de selección en la lista desplegable. El servidor generará entonces el evento [SelectedIndexChanged], que la página puede manejar.
      • Si desea manejarlo pero no inmediatamente, establezca el atributo [AutoPostBack] del componente de servidor [DropDownList] en [false]. En este caso, el servidor genera el código HTML estándar para una lista <select> para el objeto [DropDownList], sin una función JavaScript asociada. No ocurre nada cuando el usuario cambia la selección en la lista desplegable. Sin embargo, cuando el usuario envía el formulario utilizando un botón [submit], por ejemplo, el servidor podrá reconocer que se ha producido un cambio de selección. De hecho, hemos visto que el formulario enviado al servidor contiene un campo oculto [__VIEWSTATE] que representa, de forma codificada, el estado de todos los elementos del formulario enviado. Cuando el servidor recibe el nuevo formulario enviado por el cliente, puede verificar si el elemento seleccionado en la lista desplegable ha cambiado. En caso afirmativo, activará el evento [SelectedIndexChanged], que la página podrá gestionar. Para distinguir este mecanismo del anterior, algunos autores dicen que el evento "cambio de selección" se "almacena en caché" cuando se produce en el navegador. Sólo será procesado por el servidor cuando el navegador le envíe el formulario, a menudo tras hacer clic en un botón [submit].
      • Por último, si no desea manejar el evento, establezca el atributo [AutoPostBack] del componente servidor [DropDownList] en [false] y no escriba el manejador para su evento [SelectedIndexChanged].

    Una vez comprendido el mecanismo de gestión de eventos, el desarrollador no diseñará una aplicación web como una aplicación Windows. De hecho, mientras que un cambio de selección en un cuadro combinado dentro de una aplicación Windows puede utilizarse para actualizar inmediatamente la apariencia del formulario que lo contiene, es más probable que uno dude en manejar este evento inmediatamente en una aplicación web si implica un "post" del formulario al servidor-y por lo tanto un viaje de ida y vuelta entre el cliente y el servidor. Esta es la razón por la que la propiedad [AutoPostBack] de los componentes del lado del servidor está establecida por defecto en [false]. Además, el mecanismo [AutoPostBack], que se basa en scripts JavaScript generados automáticamente por el servidor web en el formulario enviado al cliente, sólo puede utilizarse si se tiene la certeza de que el navegador del cliente ha habilitado la ejecución de scripts JavaScript. Por ello, los formularios suelen construirse de la siguiente manera:

    • los componentes del lado servidor del formulario tienen su propiedad [AutoPostBack] establecida a [false]
    • el formulario tiene uno o varios botones encargados de realizar la operación [POST]
    • en el código del controlador de la página, escribes manejadores sólo para los eventos que quieres manejar, la mayoría de las veces el evento [Click] en uno de los botones.

    7.6.3. El papel del campo __VIEWSTATE

    Hemos visto que el servidor coloca sistemáticamente un campo oculto llamado __VIEWSTATE en el formulario que genera. Hemos observado que este campo representa el estado del formulario y que si este campo oculto es devuelto al servidor, éste puede reconstruir el valor anterior del formulario.       ' Transfer the selected items from l1 to l2
      ' anything to do?
      if l1.SelectedIndex = -1 then return
      dim i as integer
      ' start from the end
      for i = l1.items.count - 1 to 0, step -1

        if l1.items(i).selected then

            l1.items(i).selected = false

      next

En otras palabras, no podemos utilizar formularios de servidor ASP en una aplicación MVC. Esta es una gran revelación. De hecho, uno de los puntos clave de venta de ASP.NET es que se puede construir una aplicación web como una aplicación Windows. Esto es cierto si su aplicación no sigue la arquitectura MVC, pero no tanto en caso contrario. Sin embargo, la arquitectura MVC parece ser un concepto fundamental en el desarrollo web moderno que es difícil de ignorar.

    • la aplicación consiste en una única página que actúa como controlador
    • las vistas están representadas en esta página por diferentes contenedores, un contenedor por vista. Para mostrar una vista, hacemos visible su contenedor y ocultamos los demás

    Hemos demostrado en estos dos ejemplos que es posible construir aplicaciones web siguiendo la arquitectura MVC utilizando componentes del lado del servidor. El último ejemplo demuestra que la solución de componentes del lado del servidor es más sencilla que la solución que utiliza etiquetas HTML estándar. Nuestros dos ejemplos tenían sólo una página con múltiples vistas dentro de la misma página. Este es muy a menudo el caso de las aplicaciones que tienen menús. Tomemos el siguiente ejemplo:

    Hemos reunido en una sola página los enlaces a las aplicaciones que hemos escrito hasta ahora. Este tipo de aplicación se presta bien a una arquitectura MVC. La única diferencia es que ya no hay un controlador, sino varios.

    El [main.aspxactúa como controlador principal. Es el llamado por los enlaces de la página de inicio de la aplicación. Realizará las operaciones comunes a todas las acciones posibles y después ejecutará la acción específica asociada al enlace utilizado. A continuación, pasará el testigo a uno de los controladores secundarios, el encargado de ejecutar la acción. A partir de este momento, la comunicación se produce entre el cliente y este controlador específico. Ya no pasamos por el controlador principal [main.aspx]. Por lo tanto, ya no estamos en el marco MVC con un único controlador que filtra todas las peticiones. Cada uno de los controladores anteriores puede presentar múltiples vistas utilizando el mecanismo contenedor dentro de una única página, tal y como hemos descrito.

    El hecho de que ya no tengamos un único controlador que elija qué vistas enviar al cliente tiene sus inconvenientes. Tomemos como ejemplo la gestión de errores. Cada acción expuesta por la aplicación puede necesitar mostrar una vista de error. Cada controlador [applix.aspx] tendrá su propia vista [errores] porque ésta es simplemente un contenedor específico dentro de la página del controlador. No hay forma de tener una única vista [errores] que sea utilizada por todas las aplicaciones individuales. De hecho, tal vista típicamente incluye un enlace de vuelta al formulario con errores, y ese formulario debe ser restaurado al estado en el que fue validado para permitir al usuario corregir sus errores. Esta restauración se realiza a través del mecanismo [VIEWSTATE], que no funciona en diferentes controladores. Si las aplicaciones son desarrolladas por diferentes personas, se corre el riesgo de tener páginas de error que parezcan diferentes dependiendo de la acción elegida por el usuario, lo que socava la coherencia de la aplicación en general. Veremos un poco más adelante que ASP.NET ofrece una solución a este problema específico de compartir vistas. Esto se puede implementar como un nuevo componente de servidor que construimos nosotros mismos. El simple hecho de utilizar este componente en las distintas aplicaciones garantiza la coherencia de la aplicación global. Más difícil de gestionar es la cuestión del orden de las acciones. Cuando todas las peticiones pasan por un único controlador, éste puede verificar que la acción solicitada es compatible con la anterior. Este código de validación se encuentra en un único lugar. Aquí, tendrá que ser distribuido a través de los distintos controladores, complicando el mantenimiento de la aplicación en general.
