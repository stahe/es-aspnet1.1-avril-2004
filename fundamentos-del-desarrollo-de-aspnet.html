    4. Fundamentos del desarrollo de ASP.NET

    4.1. El concepto de aplicación web ASP.NET

    4.1.1. Introducción

    Una aplicación web es una aplicación que reúne varios documentos (código HTML, .NET, imágenes, sonidos, etc.). Estos documentos deben estar ubicados en un único directorio raíz, denominado raíz de la aplicación web. A esta raíz se asocia una ruta virtual en el servidor web. Hemos encontrado el concepto de directorio virtual para el servidor web Cassini. Este concepto también existe para el servidor web IIS. Una diferencia importante entre los dos servidores es que, en cualquier momento, IIS puede tener cualquier número de directorios virtuales, mientras que el servidor web Cassini sólo tiene uno, el especificado en el arranque. Esto significa que el servidor IIS puede servir múltiples aplicaciones web simultáneamente, mientras que el servidor Cassini sólo sirve una a la vez. En los ejemplos anteriores, el servidor Cassini siempre se iniciaba con los parámetros (<webroot>,/aspnet) que asociaban la carpeta virtual /aspnet con la carpeta física <webroot>. Por tanto, el servidor web siempre servía la misma aplicación web. Esto no nos impidió escribir y probar páginas diferentes e independientes dentro de esta única aplicación web. Cada aplicación web tiene sus propios recursos, ubicados bajo su raíz física <webroot>:

    • una carpeta [bin] donde colocar las clases precompiladas
    • un archivo [global.asax] que permite inicializar la aplicación web en su conjunto, así como el entorno de ejecución para cada uno de sus usuarios
    • un archivo [web.config] que permite configurar el comportamiento de la aplicación
    • un archivo [default.aspx] que sirve como punto de entrada de la aplicación
    • ...

    En cuanto una aplicación utiliza uno de estos tres recursos, necesita sus propias rutas físicas y virtuales. De hecho, no hay ninguna razón para que dos aplicaciones web diferentes estén configuradas de la misma manera. Todos nuestros ejemplos anteriores podían colocarse dentro de la misma aplicación (<webroot>,/aspnet) porque no utilizaban ninguno de los recursos mencionados.

    Volvamos a la arquitectura MVC recomendada al principio de este capítulo para el desarrollo de aplicaciones web:

    La aplicación web consta de archivos de clase (controlador, clases de negocio, clases de acceso a datos) y archivos de presentación (documentos HTML, imágenes, sonidos, hojas de estilo, etc.). Todos estos archivos se ubicarán en un único directorio raíz, al que a veces nos referiremos como <application-path>. Este directorio raíz estará asociado a una ruta virtual <ruta-aplicación>. El mapeo entre esta ruta virtual y la ruta física se configura a través del servidor web. Vimos que para el servidor Cassini, este mapeo ocurre cuando el servidor es lanzado. Por ejemplo, en una ventana de símbolo del sistema, lanzaríamos Cassini con:

    webserver.exe /port:80 /path:<application-path> /vpath:<application-vpath>

    En la carpeta <application-path>, dependiendo de nuestras necesidades, encontraremos:

    • la carpeta [bin] para colocar las clases precompiladas (DLLs)
    • el archivo [global.asax] cuando necesitemos realizar una inicialización durante el arranque de la aplicación o durante una sesión de usuario
    • el archivo [web.config] cuando necesitemos configurar la aplicación
    • el archivo [default.aspx] cuando necesitamos una página por defecto en la aplicación

    Para adherirse a este concepto de aplicación web, los próximos ejemplos se colocarán todos en una carpeta <application-path> específica de la aplicación, que se asociará con una carpeta virtual <application-vpath>, ya que el servidor Cassini se lanza para vincular estos dos parámetros.

    4.1.2. Configurar una aplicación web

    If <application-path> is the root of an ASP.NET application, you can use the <application-path>\web.config file to configure it. This file is in XML format. Here is an example:

    <?xml version="1.0" encoding="UTF-8" ?>

<configuration>
  <appSettings>
    <add key="name" value="tintin"/>
    <add key="age" value="27"/>
  </appSettings>   
</configuration>

    Tenga en cuenta que las etiquetas XML distinguen entre mayúsculas y minúsculas. Toda la información de configuración debe incluirse dentro del archivo <configuración> y </configuración> etiquetas. Hay muchas secciones de configuración disponibles. Aquí sólo trataremos una: la sección <appSettings> que le permite inicializar los datos utilizando la función <add> tag. La sintaxis de esta etiqueta es la siguiente:

    <add key="identifier" value="value"/>

    Cuando el servidor web lanza una aplicación, comprueba si existe un archivo llamado web.config en <ruta-aplicación>. Si es así, lo lee y almacena su información en un objeto [ConfigurationSettings], que estará disponible para todas las páginas de la aplicación mientras esté activa. La clase [ConfigurationSettings] tiene un método estático [AppSettings]:

    Para recuperar el valor de una clave C del fichero de configuración, escriba ConfigurationSettings.AppSettings("C"). Esto devuelve una cadena. Para utilizar el fichero de configuración anterior, creemos una página llamada [default.aspx]. El código VB en el archivo [default.aspx.vb] será el siguiente:

    
Imports System.Configuration
 
Public Class _default
    Inherits System.Web.UI.Page
 
    Protected name As String
    Protected age As String
 
    Private Sub Page_Load(ByVal sender As System.Object, ByVal e As System.EventArgs) Handles MyBase.Load
        'Retrieve configuration information
        name = ConfigurationSettings.AppSettings("name")
        age = ConfigurationSettings.AppSettings("age")
    End Sub
 
End Class

    Podemos ver que cuando se carga la página, se recuperan los valores de los parámetros de configuración [nombre] y [edad]. Serán mostrados por el código de presentación en [default.aspx]:

    
<%@ Page src="default.aspx.vb" Language="vb" AutoEventWireup="false" Inherits="_default" %>
<html>
    <head>
        <title>Configuration</title>
    </head>
    <body>
        Name:
        <% =name %><br/>
        Age:
        <% =age %><br/>
    </body>
</html>

    4.1.3. Aplicación, Sesión, Contexto

    4.1.3.1. El archivo global.asax

    El código del archivo [global.asax] siempre se ejecuta antes de que se cargue la página solicitada por la petición actual. Debe estar ubicado en la raíz <application-path> de la aplicación. Si existe, el archivo [global.asax] es utilizado en varios momentos por el servidor web:

    1. cuándo se inicia o finaliza la aplicación web
    2. cuando se inicia o finaliza una sesión de usuario
    3. cuando comienza la solicitud de un usuario

    Al igual que con las páginas .aspx, el archivo [global.asax] puede escribirse de diferentes maneras, en particular separando el código VB en una clase controladora y código de presentación. Esta es la opción por defecto de Visual Studio, y haremos lo mismo aquí. Normalmente no hay presentación que manejar, ya que esta función se asigna a las páginas .aspx. Por lo tanto, el contenido del archivo [global.asax] se reduce a una directiva que hace referencia al archivo que contiene el código del controlador:

    
<%@ Application src="Global.asax.vb" Inherits="Global" %>

    Observe que la directiva ya no es [Página] sino [Aplicación]. El código del controlador asociado [global.asax.vb], generado por Visual Studio, es el siguiente:

    
Imports System
Imports System.Web
Imports System.Web.SessionState
 
Public Class Global
    Inherits System.Web.HttpApplication
 
  Sub Application_Start(ByVal sender As Object, ByVal e As EventArgs)
        ' Fires when the application starts
    End Sub
 
    Sub Session_Start(ByVal sender As Object, ByVal e As EventArgs)
        ' Triggers when the session starts
    End Sub
 
    Sub Application_BeginRequest(ByVal sender As Object, ByVal e As EventArgs)
        ' Triggers at the start of each request
    End Sub
 
    Sub Application_AuthenticateRequest(ByVal sender As Object, ByVal e As EventArgs)
        ' Triggers when an authentication attempt is made
    End Sub
 
    Sub Application_Error(ByVal sender As Object, ByVal e As EventArgs)
        ' Triggered when an error occurs
    End Sub
 
    Sub Session_End(ByVal sender As Object, ByVal e As EventArgs)
        ' Triggers when the session ends
    End Sub
 
    Sub Application_End(ByVal sender As Object, ByVal e As EventArgs)
        ' Triggers when the application ends
    End Sub
 
End Class

    Tenga en cuenta que la clase controlador deriva de la clase [HttpApplication]. A lo largo de la vida de una aplicación, hay varios eventos importantes. Estos son manejados por procedimientos cuyo esqueleto se muestra arriba.

    • [Application_Start]: Recordemos que una aplicación web está "contenida" dentro de una ruta virtual. La aplicación se inicia en cuanto un cliente solicita una página situada en esta ruta virtual. A continuación, se ejecuta el procedimiento [Application_Start]. Esta será la única vez. En este procedimiento, realizaremos cualquier inicialización necesaria para la aplicación, como crear objetos cuyo tiempo de vida coincida con el de la aplicación.
    • [Application-End]: se ejecuta cuando la aplicación termina. Cada aplicación tiene asociado un tiempo de espera, configurable en [web.config], tras el cual la aplicación se considera terminada. Por tanto, es el servidor web el que toma esta decisión en función de la configuración de la aplicación. El tiempo de espera de una aplicación se define como el periodo durante el cual ningún cliente ha solicitado un recurso de la aplicación.
    • [Session-Start]/[Session_End]: Se adjunta una sesión a cada cliente a menos que la aplicación esté configurada para no tener sesiones. Un cliente no es un usuario sentado frente a una pantalla. Si un usuario ha abierto dos navegadores para interactuar con la aplicación, representan dos clientes. Un cliente se identifica por un testigo de sesión que debe incluir en cada una de sus peticiones. Este testigo de sesión es una cadena única de caracteres generada aleatoriamente por el servidor web. No puede haber dos clientes con el mismo identificador de sesión. Este testigo sigue al cliente de la siguiente manera:
      • El cliente que realiza su primera petición no envía un testigo de sesión. El servidor web lo reconoce y le asigna uno. Esto marca el inicio de la sesión, y se ejecuta el procedimiento [Session_Start]. Esto sólo ocurre una vez.
      • El cliente realiza solicitudes posteriores enviando el token que lo identifica. Esto permite al servidor web recuperar la información asociada a este token. Esto permite el seguimiento entre las distintas peticiones del cliente.
      • La aplicación puede proporcionar al cliente un formulario de fin de sesión. En este caso, el cliente inicia él mismo la finalización de la sesión. Se ejecutará el procedimiento [Session_End]. Esto ocurrirá sólo una vez.
      • Es posible que el cliente nunca solicite finalizar la sesión por sí mismo. En este caso, después de un cierto período de inactividad de la sesión -que también puede configurarse a través de [web.config]- la sesión será terminada por el servidor web. Se ejecutará entonces el procedimiento [Session_End].
    • [Application_BeginRequest]: Este procedimiento se ejecuta en cuanto llega una nueva petición. Por lo tanto, se ejecuta para cada petición de cualquier cliente. Es un buen lugar para examinar la petición antes de reenviarla a la página solicitada. Incluso puede decidir redirigirla a otra página.
    • [Application_Error]: se ejecuta cada vez que se produce un error que no es manejado explícitamente por el código en el controlador [global.asax.vb]. Aquí puede redirigir la petición del cliente a una página que explique la causa del error.

    If none of these events need to be handled, then the [global.asax] file can be ignored. This is what was done in the first examples of this chapter.

    4.1.3.2. Ejemplo 1

    Vamos a desarrollar una aplicación para entender mejor los tres momentos clave: el inicio de la aplicación, el inicio de la sesión y la petición de un cliente. El archivo [global.asax] tendrá este aspecto:

    <%@ Application src="Global.asax.vb" Inherits="global" %>

    El archivo [global.asax.vb] asociado será el siguiente:

    
Imports System
Imports System.Web
Imports System.Web.SessionState
 
Public Class global
    Inherits System.Web.HttpApplication
 
    Sub Application_Start(ByVal sender As Object, ByVal e As EventArgs)
        ' Triggered when the application starts
        ' Record the time
        Dim startApplication As String = Date.Now.ToString("T")
        ' Store it in the application context
        Application.Item("startApplication") = startApplication
    End Sub
 
    Sub Session_Start(ByVal sender As Object, ByVal e As EventArgs)
        ' Triggered when the session starts
        ' Record the time
        Dim startSession As String = Date.Now.ToString("T")
        ' Store it in the session
        Session.Item("startSession") = startSession
    End Sub
 
    Sub Application_BeginRequest(ByVal sender As Object, ByVal e As EventArgs)
        ' record the time
        Dim startRequest As String = Date.Now.ToString("T")
        ' store it in the session
        Context.Items("startRequest") = startRequest
    End Sub
End Class

    Los puntos clave del código son los siguientes:

    • El servidor web pone a disposición de la clase [HttpApplication] una serie de objetos en [global.asax.vb]:
      • Aplicación de tipo [HttpApplicationState]-representa la aplicación web-proporciona acceso a un diccionario de objetos [Application.Item] accesible a todos los clientes de la aplicación-permite compartir información entre distintos clientes-el acceso simultáneo de lectura/escritura por parte de varios clientes a los mismos datos requiere sincronización de clientes.
      • Sesión de tipo [HttpSessionState]-representa a un cliente específico-proporciona acceso a un diccionario de objetos [Session.Item] accesible a todas las peticiones de ese cliente-permite almacenar información sobre un cliente, que luego puede ser recuperada a través de las peticiones del cliente.
      • [HttpRequest] tipo solicitar - representa la solicitud HTTP actual del cliente
      • [HttpResponse] tipo Respuesta - representa la respuesta HTTP que el servidor está construyendo actualmente para el cliente
      • Servidor de tipo [HttpServerUtility] - proporciona métodos de utilidad, en particular para redirigir la solicitud a una página distinta de la prevista originalmente.
      • Contexto de tipo [HttpContext]-este objeto se vuelve a crear con cada nueva solicitud, pero es compartido por todas las páginas que participan en el procesamiento de la solicitud-permite que la información pase de una página a otra durante el procesamiento de la solicitud a través de su objeto Artículos diccionario.
    • El procedimiento [Application_Start] registra el inicio de la aplicación en una variable almacenada en un diccionario accesible a nivel de aplicación
    • El procedimiento [Session_Start] registra el inicio de la sesión en una variable almacenada en un diccionario accesible a nivel de sesión
    • El procedimiento [Application_BeginRequest] registra el inicio de la petición en una variable almacenada en un diccionario accesible a nivel de petición (i.e., disponible durante todo su procesamiento pero que se pierde al final del mismo)

    La página de destino será la siguiente página [main.aspx]:

    
<%@ Page src="main.aspx.vb" Language="vb" AutoEventWireup="false" Inherits="main" %>
<html>
    <head>
        <title>global.asax</title>
    </head>
    <body>
        session token:
        <% =token %><br/>
        Application start:
        <% =startApplication %><br/>
        Start Session:
        <% =startSession %><br/>
        Start Request:
        <% =startRequest %><br/>        
    </body>
</html>

    Esta página de presentación muestra valores calculados por su controlador [main.aspx.vb]:

    Public Class main
    Inherits System.Web.UI.Page

    Protected startApplication As String
    Protected startSession As String
    Protected startRequest As String
    Protected token As String

    Private Sub Page_Load(ByVal sender As System.Object, ByVal e As System.EventArgs) Handles MyBase.Load
        ' Retrieve application and session information
        token = Session.SessionId
        startApplication = Application.Item("startApplication").ToString
        startSession = Session.Item("startSession").ToString
        startRequest = Context.Items("startRequest").ToString
    End Sub

End Class

    El controlador simplemente recupera las tres piezas de información almacenadas en la aplicación, la sesión y el contexto por [global.asax.vb].

    1. el servidor Cassini se inicia con los parámetros (<ruta-aplicación>,/aspnet/globalasax1)

    4.1.3.3. Panorama general

    Con lo que hemos aprendido hasta ahora, podemos crear un diagrama preliminar que explique cómo funcionan un servidor web y las aplicaciones web a las que sirve:

    El diagrama anterior muestra un servidor que sirve dos aplicaciones denominadas A y B, cada una con dos clientes. Un servidor web es capaz de servir múltiples aplicaciones web simultáneamente. Estas aplicaciones son completamente independientes entre sí. Nos centraremos en la aplicación A. El procesamiento de una petición del cliente-1A a la aplicación A procederá como sigue:

    • El cliente 1A solicita un recurso al servidor web que pertenece al dominio de la aplicación A. Esto significa que solicita un URL de la forma [http://machine:port/VA/ressource], donde VA es la ruta virtual de la aplicación A.
    • If the web server detects that this is the first request for a resource from Application A, it triggers the [Application_Start] event in the [global.asax] file of Application A. An [ApplicationA] object of type [HttpApplicationState] will be created. The various parts of the application will store data with [Application] scope in this object, i.e., data concerning all users. The [ApplicationA] object will exist until the web server unloads application A.
    • If the web server also detects that it is dealing with a new client for Application A, it will trigger the [Session_Start] event in the [global.asax] file of Application A. An [Session-1A] object of type [HttpSessionState] will be created. This object will allow Application A to store [Session] scope objects, i.e., objects belonging to a specific client. The [Session-1A] object will exist as long as client 1A makes requests. It will enable tracking of this client. The web server detects that it is dealing with a new client in two cases:
      • el cliente no ha enviado un testigo de sesión en las cabeceras HTTP de su solicitud
      • el cliente ha enviado un testigo de sesión que no existe (mal funcionamiento del cliente o intento de pirateo) o que ya no existe. Un testigo de sesión caduca tras un cierto periodo de inactividad del cliente (20 minutos por defecto con IIS). Este periodo de expiración es configurable.
    • En todos los casos, el servidor web activará el evento [Application_BeginRequest] en el archivo [global.asax]. Este evento inicia el procesamiento de la petición de un cliente. Es habitual no manejar este evento y pasar el control a la página solicitada por el cliente, que procesará la petición. También podemos utilizar este evento para analizar la petición, procesarla y decidir qué página debe enviarse como respuesta. Utilizaremos esta técnica para implementar una aplicación que siga la arquitectura MVC de la que hemos hablado.
    • Una vez pasado el filtro en [global.asax], la petición del cliente se pasa a una página .aspx que procesará la petición. Veremos más adelante que es posible pasar la petición a través de un filtro formado por múltiples páginas. La última página será la responsable de enviar la respuesta al cliente. Las páginas pueden añadir información que hayan calculado a la petición inicial del cliente. Pueden almacenar esta información en el archivo Context.Items colección. De hecho, todas las páginas que intervienen en el procesamiento de la solicitud de un cliente tienen acceso a este conjunto de datos.
    • El código de las distintas páginas tiene acceso a los depósitos de datos representados por los objetos [ApplicationA], [Session-1A], ... Es importante recordar que el servidor web procesa simultáneamente varios clientes para la aplicación A. Todos estos clientes tienen acceso al objeto [Aplicación A]. Si necesitan modificar datos en este objeto, es necesaria la sincronización de clientes. Cada cliente XA también tiene acceso a la reserva de datos [Sesión-XA]. Dado que está reservado para ellos, no es necesaria la sincronización.
    • El servidor web sirve varias aplicaciones web simultáneamente. No hay interferencias entre los clientes de estas distintas aplicaciones.

    A partir de estas explicaciones, podemos resumir los siguientes puntos:

    • En un momento dado, un servidor web atiende a varios clientes simultáneamente. Esto significa que no espera a que termine una solicitud para procesar otra. Por lo tanto, en el momento T se están procesando varias peticiones que pertenecen a distintos clientes para distintas aplicaciones. El código de procesamiento que se ejecuta simultáneamente en el servidor web se denomina a veces hilos de ejecución.
    • Los hilos de ejecución de los clientes de diferentes aplicaciones web no interfieren entre sí. Hay aislamiento.
    • Hilos de ejecución de los clientes de la misma aplicación pueden necesitar compartir datos:
      • Hilos de ejecución de las solicitudes de dos clientes diferentes (no el mismo token de sesión) pueden compartir datos a través de la función [Aplicaciónobjeto.
      • Hilos de ejecución para solicitudes sucesivas del mismo cliente pueden compartir datos a través del [Sesiónobjeto.
      • Hilos de ejecución para páginas sucesivas que procesan el misma solicitud de un determinado cliente pueden compartir datos a través del [Contextoobjeto.

    4.1.3.4. Ejemplo 2

    Vamos a desarrollar un nuevo ejemplo que ilustre lo que acabamos de ver. Colocaremos los siguientes archivos en la misma carpeta:

    [global.asax]

    <%@ Application src="Global.asax.vb" Inherits="global" %>

    [global.asax.vb]

    
Imports System
Imports System.Web
Imports System.Web.SessionState
 
Public Class global
    Inherits System.Web.HttpApplication
 
    Sub Application_Start(ByVal sender As Object, ByVal e As EventArgs)
        ' Fires when the application starts
        ' Initialize client counter
        Application.Item("nbRequests") = 0
    End Sub
 
    Sub Session_Start(ByVal sender As Object, ByVal e As EventArgs)
        ' Triggered when the session starts
        ' Initialize request counter
        Session.Item("nbRequests") = 0
    End Sub

    4.1.3.5. La necesidad de sincronizar los clientes de una aplicación

    En la aplicación anterior, el contador de peticiones realizadas a la aplicación se incrementa en el procedimiento [Form_Load] de la página [main.aspx] del siguiente modo:

            ' one more request for the application
        Application.Item("nbRequests") = CType(Application.Item("nbRequests"), Integer) + 1

    Esta instrucción, aunque sencilla, requiere varias instrucciones del procesador para ejecutarse. Supongamos que requiere tres:

    1. lectura del contador
    2. incrementar el contador
    3. escribir el contador

    El servidor web se ejecuta en una máquina multitarea, lo que significa que a cada tarea se le concede el procesador durante unos milisegundos antes de perderlo y recuperarlo después de que todas las demás tareas hayan tenido también su parte de tiempo. Supongamos que dos clientes, A y B, hacen una petición al servidor web al mismo tiempo. Digamos que el cliente A va primero, entra en el procedimiento [Form_Load] en [main.aspx.vb], lee el contador (=100), y luego es interrumpido porque su porción de tiempo ha expirado. Supongamos ahora que es el turno del cliente B y que éste corre la misma suerte: llega al método , lee el valor del contador (=100), pero no tiene tiempo de incrementarlo. Los clientes A y B tienen ambos un valor de contador de 100. Supongamos que vuelve a ser el turno del cliente A: incrementa su contador, lo pone a 101 y termina. Ahora es el turno del cliente B, que tiene en su poder el antiguo valor del contador, no el nuevo. Por lo tanto, también establece el valor del contador en 101 y finaliza. El valor del contador de peticiones de la aplicación es ahora incorrecto.

    4.1.3.6. Sincronización de clientes

    El problema destacado en la aplicación anterior es un problema clásico (pero no fácil de resolver) de acceso exclusivo a un recurso. En nuestro caso concreto, debemos asegurarnos de que dos clientes, A y B, no puedan estar en la secuencia de código al mismo tiempo:

    1. lectura del contador
    2. incrementar el contador
    3. escribir en el contador

    Una secuencia de código de este tipo se denomina sección crítica. Requiere la sincronización de los hilos que la ejecutan simultáneamente. La plataforma .NET ofrece varias herramientas para asegurar esto. Aquí utilizaremos la clase [Mutex].

    Aquí, sólo utilizaremos los siguientes constructores y métodos:

    public Mutex()
    crea un objeto de sincronización M
    public bool WaitOne()
    Thread T1, que ejecuta el M.WaitOne() solicita la propiedad del objeto de sincronización M. Si el Mutex M no está en posesión de ningún thread (caso inicial), se "regala" al thread T1, que lo ha solicitado. Si, un poco más tarde, el hilo T2 realiza la misma operación, se bloqueará. Esto se debe a que un mutex sólo puede pertenecer a un hilo a la vez. Será liberado cuando el hilo T1 libere el mutex M que posee. Por lo tanto, varios hilos pueden bloquearse mientras esperan el mutex M.
    public void ReleaseMutex()
    El hilo T1 que realiza la M.ReleaseMutex() cede la propiedad del Mutex M. Cuando el thread T1 pierde el procesador, el sistema puede asignarlo a uno de los threads que esperan el Mutex M. Sólo uno lo obtendrá a su vez; los demás que esperan M permanecen bloqueados

    Un Mutex M gestiona el acceso a un recurso compartido R. Un hilo solicita el recurso R mediante M.WaitOne() y lo libera a través de M.ReleaseMutex(). Una sección crítica de código que debe ser ejecutada por un solo hilo a la vez es un recurso compartido. La sincronización de la ejecución de la sección crítica se puede lograr de la siguiente manera:

    M.WaitOne()
' the thread is the only one entering here
' critical section
....
M.ReleaseMutex()

    donde M es un Mutex objeto. Por supuesto, nunca debe olvidarse de liberar un objeto Mutex que ya no se necesita, para que otro hilo pueda entrar en la sección crítica a su vez; de lo contrario, los hilos que esperan un Mutex que nunca se libera nunca tendrán acceso al procesador. Además, hay que evitar una situación de bloqueo en la que dos subprocesos se esperan mutuamente. Considere las siguientes acciones que ocurren en secuencia:

    • un hilo T1 adquiere la propiedad de un Mutex M1 para acceder a un recurso compartido R1
    • un hilo T2 adquiere un Mutex M2 para acceder a un recurso compartido R2
    • El hilo T1 solicita el Mutex M2. Se bloquea.
    • El hilo T2 solicita el Mutex M1. Se bloquea.

    Aquí, los hilos T1 y T2 se están esperando mutuamente. Esta situación se produce cuando los hilos necesitan dos recursos compartidos: el recurso R1 controlado por Mutex M1 y el recurso R2 controlado por Mutex M2. Una posible solución es solicitar ambos recursos al mismo tiempo utilizando un único mutex M. Pero esto no siempre es posible, especialmente si resulta en un largo bloqueo de un recurso costoso. Otra solución es que un hilo que tenga M1 y no pueda obtener M2 libere M1 para evitar el bloqueo.

    4.1.3.7. Gestión de tokens de sesión

    Hemos hablado muchas veces del testigo de sesión intercambiado entre el cliente y el servidor web. Repasemos cómo funciona:

    • El cliente realiza una petición inicial al servidor. No envía un testigo de sesión.
    • Dado que el testigo de sesión no aparece en la solicitud, el servidor reconoce que se trata de un nuevo cliente y le asigna un testigo. Asociado a este token hay un objeto [Session] que se utilizará para almacenar información específica de este cliente. El token acompañará a todas las peticiones de este cliente. Se incluirá en las cabeceras HTTP de la respuesta a la primera petición del cliente.

    4.2. Recuperar información de una solicitud de cliente

    4.2.1. El ciclo cliente-servidor de solicitud-respuesta web

    Repasemos el contexto cliente-servidor de una aplicación web:

    La solicitud de una aplicación web por parte de un cliente se procesa del siguiente modo:

    1. El cliente abre una conexión TCP/IP al puerto P del servicio web en la máquina M que aloja la aplicación web
    2. envía una serie de líneas de texto a través de esta conexión según el protocolo HTTP. Este conjunto de líneas forma lo que se denomina la petición del cliente. Tiene la siguiente forma:

    Una vez enviada la solicitud, el cliente espera la respuesta.

    1. La primera línea de la cabecera HTTP especifica la acción solicitada al servidor web. Puede adoptar varias formas:
      • GET HTTP URL/<versión>, donde <versión> es actualmente 1.0 o 1.1. En este caso, la solicitud no incluye la sección [Documento
      • POST HTTP URL/<version>. En este caso, la solicitud incluye una sección [Documento], que suele ser una lista de información destinada a la aplicación web
      • PUT HTTP URL/<version>. El cliente envía un documento en la sección [Documento] y desea almacenarlo en el servidor en el URL

    Cuando el cliente desea transmitir información a la aplicación web a la que se ha conectado, dispone de dos métodos principales:

    • (continuación)
      • su petición es [GET enriched_url HTTP/<versión>] donde enriched_url tiene la forma [url?param1=val1&param2=val2&...]. Además del URL, el cliente transmite una serie de informaciones de la forma [clave=valor].
      • Su solicitud es [POST enriched-url HTTP/<version>]. En la sección [Documento], envían información en el mismo formato que antes: [param1=val1&param2=val2&...].
    1. En el servidor, toda la cadena de procesamiento de solicitudes del cliente tiene acceso a la solicitud a través de un objeto global denominado Solicitar. El servidor web ha colocado toda la solicitud del cliente en este objeto en un formato que exploraremos en breve. La aplicación solicitada procesará este objeto y construirá una respuesta para el cliente. Esta respuesta está disponible en un objeto global llamado Respuesta. El papel de la aplicación web es construir un [Respuestadel objeto [Solicitar]. La cadena de procesamiento también tiene los objetos globales [Aplicación] y [Sesión], de la que ya hemos hablado y que le permitirá compartir datos entre distintos clientes (Aplicación) o entre sucesivas peticiones de un mismo cliente (Sesión).
    2. La aplicación enviará su respuesta al servidor utilizando el objeto [Response]. Una vez en la red, esta respuesta tendrá el siguiente formato HTTP:

    Una vez enviada esta respuesta, el servidor cerrará la conexión de red entrante (a menos que el cliente le haya indicado que no lo haga).

    1. El cliente recibirá la respuesta y, a su vez, cerrará la conexión (en el lado saliente). Lo que se haga con esta respuesta dependerá del tipo de cliente. Si el cliente es un navegador y el documento recibido es un documento HTML, se mostrará. Si el cliente es un programa, la respuesta será analizada y procesada.
    2. El hecho de que, tras el ciclo solicitud-respuesta, se cierre la conexión que une al cliente con el servidor hace de HTTP un protocolo sin estado. Durante la siguiente petición, el cliente establecerá una nueva conexión de red con el mismo servidor. Dado que ya no se trata de la misma conexión de red, el servidor no tiene forma (en los niveles TCP/IP y HTTP) de vincular esta nueva conexión a una anterior. Es el sistema de testigos de sesión el que permitirá este enlace.

    4.2.2. Recuperación de la información enviada por el cliente

    A continuación examinaremos ciertas propiedades y métodos del objeto [Request] que permiten al código de la aplicación acceder a la solicitud del cliente y, por tanto, a la información que ha transmitido. El objeto [Request] es de tipo [HttpRequest]:

    Esta clase tiene numerosas propiedades y métodos. Nos interesan las propiedades HttpMethod, QueryString, Forma, y Parámetros que nos permitirán acceder a los elementos de la cadena de información [param1=val1&param2=val2&...].

    HttpMethod as String
    método de solicitud del cliente: GET, POST, HEAD, ...
    QueryString as NameValueCollection
    colección de elementos de la cadena de consulta param1=val1&param2=val2&... de la primera línea HTTP [método]?param1=val1&param2=val2&... donde [método] puede ser GET, POST, HEAD.
    Form as NameValueCollection
    colección de elementos de la cadena de consulta param1=val1&param2=val2&.. encontrada en la parte [Document] de la petición (método POST).
    Params as NameValueCollection
    combina varias colecciones: QueryString, Formulario, ServerVariables, Cookies en una sola colección.

Imports System
Imports System.Collections.Specialized
 
Public Class main

    Protected infosQueryString As ArrayList
    Protected WithEvents lstQueryString As System.Web.UI.WebControls.ListBox
    Protected WithEvents lstForm As System.Web.UI.WebControls.ListBox
    Protected infosForm As ArrayList
 
    Private Sub Page_Init(ByVal sender As Object, ByVal e As System.EventArgs) Handles MyBase.Init
        ' Store the client's request in request.txt in the application folder

        Me.Request.SaveAs(requestFileName, True)
    End Sub
 
    Private Sub Page_Load(ByVal sender As System.Object, ByVal e As System.EventArgs) Handles MyBase.Load
        ' Retrieve the entire collection of QueryString information

        ' retrieve the keys from the collection
        Dim keys() As String = data.AllKeys
        ' Iterate through the array of keys
        Dim values() As String
        For Each key As String In keys
            ' values associated with the key
            values = data.GetValues(key)
            ' a single value?
            If values.Length = 1 Then
                info.Add(key + "=" + values(0))
            Else
                ' multiple values
                For ivalue As Integer = 0 To values.Length - 1
                    info.Add(key + "(" + ivalue.ToString + ")=" + values(ivalue))
                Next
            End If
        Next
        ' return the result
        Return info
    End Function
End Class

    Los puntos clave de este código son los siguientes:

    • En [Form_Load], la página recupera las dos colecciones [QueryString] y [Form]. Utiliza una función [getValues] para colocar el contenido de estas dos colecciones en dos objetos [ArrayList], que contendrán cadenas de la forma [clave=valor] si la clave de la colección está asociada a un único valor, o [clave(i)=valor] si la clave está asociada a varios valores.
    • A continuación, cada uno de los objetos [ArrayList] se vincula a uno de los objetos [ListBox] de la página de presentación mediante dos sentencias:
      • [ListBox.DataSource=ArrayList] y [ListBox.DataBind]. Esta última instrucción transfiere los elementos de [DataSource] a la colección [Items] del objeto [ListBox]

    Observe que ninguno de los dos objetos [ListBox] se crea explícitamente mediante una operación [New]. Podemos deducir que cuando la etiqueta <asp:listbox id="xx">...<asp:listbox/> está presente, el propio servidor web crea el objeto [ListBox] referenciado por el atributo [id] de la etiqueta.

    • La función [getValeurs] utiliza el objeto [NameValueCollection] que se le pasa como parámetro para devolver un resultado de tipo [ArrayList].

    4.3. Implantación de una arquitectura MVC

    4.3.1. El concepto

    Concluyamos este largo capítulo implementando una aplicación construida según el patrón MVC (Modelo-Vista-Controlador). Una aplicación web diseñada según este patrón tiene este aspecto:

    • el cliente envía sus peticiones a un componente específico de la aplicación denominado controlador
    • El controlador analiza la petición del cliente y la ejecuta. Para ello, se apoya en clases que contienen la lógica de negocio de la aplicación y clases de acceso a datos.
    • En función del resultado de la ejecución de la solicitud, el controlador elige enviar una página específica en respuesta al cliente

    En nuestro modelo, todas las peticiones pasan a través de un único controlador, que actúa como orquestador de toda la aplicación web. La ventaja de este modelo es que todo lo que hay que hacer antes de cada solicitud se puede consolidar dentro del controlador. Supongamos, por ejemplo, que la aplicación requiere autenticación. Esto se realiza una sola vez. Una vez realizada con éxito, la aplicación almacenará la información relacionada con el usuario que acaba de autenticarse en la sesión. Dado que un cliente puede llamar directamente a una página de la aplicación sin autenticarse, cada página tendrá que comprobar en la sesión que la autenticación se ha completado. Si todas las peticiones pasan por un único controlador, es éste el que puede realizar esta tarea. Las páginas a las que finalmente se pase la petición no tendrán que hacerlo.

    4.3.2. Control de una aplicación MVC sin sesión

    Por lo que hemos visto hasta ahora, se podría pensar que el fichero [global.asax] podría servir como controlador. De hecho, sabemos que todas las peticiones pasan a través de él. Por lo tanto, está bien posicionado para controlarlo todo. La siguiente aplicación lo utiliza con este fin. Su ruta virtual será [http://localhost/mvc1/main.aspx]. Para especificar lo que desea, el cliente añadirá un parámetro action=value al URL. Dependiendo del valor del parámetro [action], el controlador [global.asax] dirigirá la petición a una página concreta:

    1. [main.aspx] si el parámetro action no está definido o si action=main
    2. [action1.aspx] if action=acción1
    3. [unknown.aspx] si la acción no entra en los casos 1 y 2

    Las páginas [main.aspx, action1.aspx, unknown.aspx] simplemente muestran el valor de [action] que desencadenó su visualización. A continuación enumeramos los ocho archivos de esta aplicación y proporcionamos comentarios cuando es necesario:

Imports System
Imports System.Web
Imports System.Web.SessionState
 
Public Class Global
    Inherits System.Web.HttpApplication
 
    Sub Application_BeginRequest(ByVal sender As Object, ByVal e As EventArgs)
        ' retrieves the action to be performed
        Dim action As String
        If Request.QueryString("action") Is Nothing Then
            action = "main"
        Else
            action = Request.QueryString("action").ToString.ToLower
        End If
        ' Set the action in the request context
        Context.Items("action") = action
        ' execute the action
        Select Case action
            Case "main"
                Server.Transfer("main.aspx", True)
            Case "action1"
                Server.Transfer("action1.aspx", True)
            Case Else
                Server.Transfer("unknown.aspx", True)
        End Select
    End Sub
End Class

    Puntos a tener en cuenta:

    • Interceptamos todas las peticiones de los clientes en el procedimiento [Application_BeginRequest], que se ejecuta automáticamente al inicio de cada nueva petición realizada a la aplicación.
    • En este procedimiento, tenemos acceso al objeto [Request], que representa la petición HTTP del cliente. Como esperamos un URL de la forma [http://localhost/mvc1/main.aspx?action=xxbuscamos una clave llamada [action] en la colección [Request.QueryString]. Si no está presente, establecemos el valor por defecto de [action] en "main".
    • El valor del parámetro [action] se coloca en el objeto [Context]. Al igual que los objetos [Application, Session, Request, Response, Server], este objeto es global y accesible desde cualquier código. Este objeto se pasa de una página a otra si la solicitud es gestionada por varias páginas, como será el caso aquí. Se elimina en cuanto se envía la respuesta al cliente. Por lo tanto, su tiempo de vida se limita a la duración del procesamiento de la solicitud.
    • Dependiendo del valor del parámetro [action], la petición se pasa a la página adecuada. Para ello, utilizamos el objeto global [Servidor] que, gracias a su método, nos permite transferir la petición actual a otra página. Su primer es el nombre de la página de destino, y el segundo es un booleano que indica si se transfieren o no las colecciones [QueryString] y [Form] a la página de destino. En este caso, la respuesta es sí.

    4.3.3. Controlar una aplicación MVC con sesiones

    La mayoría de las veces, las distintas peticiones de un cliente a una aplicación necesitan compartir información. Hemos visto una posible solución a este problema: almacenar la información a compartir en el objeto [Session] de la petición. En efecto, este objeto es compartido por todas las peticiones y es capaz de almacenar información de la forma (clave, valor), donde clave es de tipo [String] y valor es cualquier tipo derivado de [Object].

    En el ejemplo anterior, las distintas páginas asociadas a las diferentes acciones se llamaban en el procedimiento [Application_BeginRequest] del fichero [global.asax.vb]:

    
    Sub Application_BeginRequest(ByVal sender As Object, ByVal e As EventArgs)
        ' retrieve the action to be performed
        Dim action As String
        If Request.QueryString("action") Is Nothing Then
            action = "main"
        Else
            action = Request.QueryString("action").ToString.ToLower
        End If
        ' Set the action in the request context
        Context.Items("action") = action
        ' execute the action
        Select Case action
            Case "main"
                Server.Transfer("main.aspx", True)
            Case "action1"
                Server.Transfer("action1.aspx", True)
            Case Else
                Server.Transfer("unknown.aspx", True)
        End Select
    End Sub

    Resulta que en el procedimiento [Application_BeginRequest], el objeto [Session] no es accesible. Lo mismo ocurre en la página a la que se transfiere la ejecución. Por lo tanto, este modelo no se puede utilizar para una aplicación con una sesión. Podemos asignar el rol de controlador a cualquier página, por ejemplo [default.aspx]. Los archivos [global.asax, global.asax.vb] se eliminan y se sustituyen por los archivos [default.aspx, default.aspx.vb]:

    [default.aspx]

Imports System
Imports System.Web
Imports System.Web.SessionState
 
Public Class Controller
    Inherits System.Web.UI.Page
 
    Private Sub Page_Load(ByVal sender As System.Object, ByVal e As System.EventArgs) Handles MyBase.Load
        ' retrieve the action to be performed
        Dim action As String
        If Request.QueryString("action") Is Nothing Then
            action = "main"
        Else
            action = Request.QueryString("action").ToString.ToLower
        End If
 
        ' Set the action in the request context
        Context.Items("action") = action
        ' retrieve the previous action if it exists
        Context.Items("actionPrec") = Session.Item("actionPrec")
        If Context.Items("actionPrec") Is Nothing Then Context.Items("actionPrec") = ""
        ' the current action is saved in the session
        Session.Item("actionPrec") = action
 
        ' execute the action
        Select Case action
            Case "main"
                Server.Transfer("main.aspx", True)
            Case "action1"
                Server.Transfer("action1.aspx", True)
            Case Else
                Server.Transfer("unknown.aspx", True)
        End Select
    End Sub
End Class

    Para poner de relieve el mecanismo de la sesión, las distintas páginas mostrarán no sólo la acción actual, sino también la acción precedente. Para una secuencia de acciones A1, A2, ..., An, cuando se produce la acción Ai, el controlador anterior:

    • sitúa la acción actual Ai en el contexto
    • recupera la acción precedente Ai-1 de la sesión. Si no hay ninguna (como en el caso de la acción A1), establece la acción anterior en una cadena vacía.
    • coloca la acción actual Ai en la sesión para sustituir a Ai-1
    • transfiere la ejecución a la página correspondiente
